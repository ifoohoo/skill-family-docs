# 环境探测与文档站接入

`skill-family-docs-setup` 负责诊断项目的文档站运行条件，并在获批后完成简洁、无负担的本地接入。严格遵循“零写入只读诊断 → 展示精确计划与文件影响 → 取得明确同意 → 复核未漂移后执行 → 只读复验”的事务流程。

## 一、判定请求模式与零写入守则

- **明确只读请求**（如“只读检查”“别改文件”）：输出诊断结论与参考方案即可，可附一段可复制的接入提示词，不追问是否立即修改。
- **常规就绪检查**（如“setup”“检查环境是否就绪”）：先完成只读检查；已就绪则直接汇报结果，存在可安全补齐的缺项时展示精确计划并询问是否执行。
- **首次接入请求**（如“帮我接入文档站”“准备环境并接线”）：启动接入事务，但首次指令不代表批准尚未展示的文件修改；必须先展示完整计划并等待用户明确确认。
- **确认执行**：收到用户明确同意后，在落盘前复核依赖版本、包管理器、目标路径与现有文件均未发生漂移；一旦发生漂移，立即停止写入并重新展示更新后的计划。

授权前严禁修改项目文件、`package.json`、锁文件、`public-release.json`、覆盖快照、生成产物、缓存或宿主持久状态，也不得执行隐式安装依赖的 `npx --yes` 或 `npm exec --yes`。授权前的 Git 查询统一设置 `GIT_OPTIONAL_LOCKS=0`，确保工作区与 `.git/index` 字节完全不变。

## 二、零写入环境与仓库探测

1. **核对 Node.js 与 CLI 获取顺序**：读取项目权威版本约束（`package.json` 的 `engines.node`、`.node-version` 等；存在多源冲突时停止并说明，不猜测版本）、包管理器与锁文件。CLI 获取顺序严格遵守：
   - 优先复用已有精确依赖；
   - 不可复用时，若项目政策允许则新增精确项目开发依赖；
   - 项目禁止持久依赖但明确允许外部 QA 工具时，才制定精确版本的临时调用计划；
   - 上述来源都不符合项目政策时，状态记为“不满足前提”。
2. **核实官方精确版本与公开合同**：通过宿主网络工具或只读命令读取官方 npm registry 上 `skill-family-doc-render` 的最新稳定版（不写入缓存或日志文件）；CLI 尚未安装时，通过标准输出管道从精确版本包读取公开 README 与 Schema，不能先安装再补查合同；无法零写入取得必要合同时，状态记为“不满足前提”。
3. **检查或设计站点与覆盖配置**：完整解析结构化配置文件或检索完整文件内容后核对匹配区段（被截断的输出不能证明字段不存在）。核对 `public-release.json` 中目标仓库的 `site.dir`、`site.target`、`site.pages`、`site.versionSources` 及 `site.coverage.inputs` 实际命中的文件清单（仅支持相对路径、`*` 与 `**`；纳入源码、权威文档与版本源文件，排除缓存、日志、`node_modules` 与生成产物）。
   - 新建站点统一采用简洁现代配置：`site.format: "markdown-v2"` 与 `site.template: "modern"`。若发布至独立公开静态文档仓，一律命名为 `<owner>/<id>-site`（`main:/` 部署静态产物，打 `site-v{version}` 标签），在 `site` 中填写 `publicSiteRepo` 与 `https://` `pagesUrl`（多包工作区同时填写 `publicReadmePaths`），并在关联公开插件/npm 包的 GitHub `About -> Website (homepageUrl)`、`package.json#homepage` 与公开 `README.md` 首屏三处同步放置显式 GitHub Pages 入口，关停旧的插件仓内重复 Pages。
   - `pages.json` 只需声明 `site: { title, tagline, version? }`、`groups: [{ id, title }]` 与 `pages: [{ id, title, navTitle?, summary?, group }]`，无需填写死板的 `role`、`kind`、`inPager` 枚举槽位；同时确认 `<id>.md` 文件规划。
4. **检查既有门禁与中文写作配置**：
   - 记录项目已有的文档/发布检查脚本（如 `check:release-docs` 与 `release-skill` `hooks.docs`）及其命令顺序与失败传播。
   - 读取 `../skill-family-docs-build-site/references/expression-registry.md`，分别检查本地 `humanize-rewrite` 入口与项目根 `agent-methods.yaml`（推荐配置为 `shuorenhua`，同时尊重项目已有合法覆盖选择；配置检查全程本地只读，绝不自动发起模型调用，表达配置缺失不阻断纯渲染或机械检查）。
5. **处理已有自定义站点并执行只读预检**：
   - 若项目已存在自定义文档生成器、手写 HTML 或自有构建脚本，不直接判为“不适用”，也不强行修补旧脚本，而是按路径与命令争用给出 **保留现状**、**兼容接入**、**有冲突（列明争用点）** 或 **显式迁移** 四选一建议。
   - 配置与 CLI 均已就绪时，运行只读 `skill-family-doc-render --check-project --repo <name>`（按需配合 `--check-layout` 与 `--check-stale-limits`）。

## 三、诊断状态与精确计划格式

回复首行标明唯一诊断状态：`已就绪`、`已接入，站点待处理`、`可接入`、`有冲突`、`不满足前提` 或 `保留现状`（并单独汇报中文表达方法配置状态）。状态为“可接入”时，计划必须逐项列明：

1. 官方核实的精确已发布版本、查询方式与来源地址。
2. 当前包管理器的完整安装或调用命令，包含会影响行为的环境变量、缓存与日志位置（复用已有依赖时写明“保持不变”）。
3. 将创建、修改和保持不变的具体路径；对每个文件列出全部新增或变化字段及其精确值，禁止留空待执行时再定。
4. 预计执行的命令、工作目录与本地影响范围。
5. 明确不会执行的动作（宿主插件安装、远端推送、软件发布、整站正文生成、未获批迁移与无关文件改动）。
6. 执行完成后的可验证成功信号。

## 四、按获批计划执行与复验

1. 首次写入前重跑关键只读检查；若存在任何未定字段，或版本、路径、文件内容与冲突状态已变化，不得先执行计划的一部分，须重新展示完整计划并取得同意。
2. 严格按获批命令、环境变量与路径写入精确依赖、简洁 `public-release.json` 站点配置、弹性 `pages.json` 及门禁脚本；将 `--check-project --repo <name>`、`--check-layout --repo <name>` 与 `--check-stale-limits --repo <name>` 串联进现有文档门禁，不替换或跳过原检查（采用外部 QA 临时调用路径时不修改 `package.json` 或锁文件）。
3. 仅当站点 `.md` 源文件已就位且覆盖清单核实无误时，才执行 `--refresh-coverage --repo <name>`；若配置已完成但正文尚未编写，明确报告“接入配置完成，等待首次生成”，由 `skill-family-docs-build-site` 接力创作，绝不提前刷新覆盖锁。未接入发布工具的项目如实标注“本地接入完成，发布集成未配置”。重复执行相同接入请求时保持配置与锁文件字节幂等不变。
