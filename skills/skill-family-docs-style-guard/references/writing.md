# 写作相位：起草技术文档

本文件在动笔前读一遍，带着它写。审校时不要回头读这份，去读 `revision.md`。

## 动笔前冻结读者合同

写下四个答案，它们不是正文模板：

- 目标读者是谁，允许假定哪些前置知识；
- 读者读完要能作出什么判断、完成什么动作；
- 手里最硬的三样材料是什么（代码、配置、错误现象、实测数据、权威出处）；
- 哪些版本、路径、状态、条件和授权边界不得在写作中漂移。

读者不是「所有人」。规格可以声明前置知识，教程必须补齐背景。没声明的先验知识不许偷偷成为阅读前提。

## 材料门槛

技术主题手里没材料就不开长篇。材料不够时按顺序处理：能检索的先检索；依赖用户亲历或判断的，一次问完最多三个问题；仍不够的缩短篇幅。三条路都走不通，这个主题此刻就不该写。留下空白占位或换说法复读，是把缺材料的事实藏起来，比不写更糟。

## 开头让读者站稳

长文档开头尽快回答四件事：这是什么文档、当前什么状态、主要结论或目标是什么、读者接下来要做什么。形式自选，一段话或短列表都行，不固定标题。短文标题加首句已经答完时，直接进正文，不另加摘要区。

按文档类型排第一屏的信息需求（不是标题模板）：

- 报告：先结论、结论效力和证据边界；
- 方案：先改变什么、为什么、不改变什么；
- 教程：先使用场景、预期结果、必要准备；
- README：先解决什么问题、适合谁、最短上手路径、当前限制。

## 从一个使用场景起稿

每条主要功能先落到读者会遇到的问题。沿同一个场景写清适用条件、必要输入、操作入口、预期结果和失败后的去处，让读者不必把散落的说明自己拼成流程。这些是信息要求，不是固定标题；短页面可以用几段正文完成，复杂任务再按读者操作顺序分节。

命令、字段和参数只在场景走到对应步骤时出现，并就近说明用途。参考页保存完整清单，任务页不先倒出接口全集。库型项目直接讲安装、最小调用、输入输出和异常，不要求读者先了解文档插件怎样工作。

## 文章按读者疑问往前走

每段回答上一段最可能引出的下一个问题。先讲发生了什么，读者会问为什么；先给约定，读者会问凭什么；先讲通常情况，读者会问这次哪里特殊。这些关系交替用，不排固定结构。

关键概念、命令和状态名在第一次被依赖前解释。术语第一次出现给一句人话解释或英文全称，走到那里再出现，不在开头一次性倒完背景。

## 句子先把主干交出来

普通中文先说谁做了什么，再补原因、条件和例子。一句里「的」超过三个，先找真正做事的人放到句首，剩下的沿动作往后接。一句话只承载一个主要判断；结论、原因、边界、后果要同时说时，按语义节点拆开。

让句子有松有紧：多数段落两三句话，也允许一段讲长。连续短句像敲桌子，连续长句让人等不到落脚处。逗号让同一口气继续，句号让一件事落下。

检测器可能提示句长整齐、连词密集或长句偏多。这些只用来定位值得重读的段落，不能按比例删词，也不能为制造长短差而补一句或拉长一句。回到读者任务判断：动作是否明确，关系是否连贯，一个句子是否塞进了多个主要判断。动词被压成名词时，找回谁做了什么，再改成直接动作。

## 只解释任务需要的架构

架构说明回答三类问题：哪个组件负责什么，内容或控制怎样流动，当前限制为什么会出现。只写读者完成任务、选择接入方式或定位故障需要的部分。

例如，解释一次知识站刷新时，可以沿同一操作说明文档技能怎样读取事实并修改 Markdown，配置和页面清单怎样选择内容与导航，渲染器怎样生成并检查页面，发布文档检查怎样只读验证结果。正文写错时回到 Markdown 和事实来源；产物与正文不一致时检查渲染；是否已经发布则查正式发布证据。因果和限制必须来自代码、接口或权威设计。材料不足时缩短解释，不拿目录树、函数清单或未来设想充数。

## 代码与字段的上下文

代码块前后至少有一处说明用途、输入、结果或原因，不写「以上代码展示了」这种空话，也不逐行复述代码。命令出现时说明它要做什么，字段出现时说明它表达什么事实，状态码说明它会影响什么判断。

## 列表和表格服从读者任务

读者需要比较、计数、执行或逐项核对时用列表。表格只放维度相同、字段稳定的比较和枚举；长因果链、例外和裁决理由留在正文。三项并列不自动列表化，短而紧密的并列留在句中。

## 作者位置

技术文档让作者隐身，以所写的产品、框架名或「开发者 / 我们」作主语。不用第二人称指着读者说教，命令式句型自然指向操作即可。

## 动笔前最后看一眼

只检查六件事：替谁讲清楚；读者允许知道什么；读完要做什么；最硬的三样材料是什么；哪些事实不能改；读者看完上一段会追问什么。答得出来就动笔。
