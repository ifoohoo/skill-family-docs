# 审校相位：围绕读者任务集中改稿

本文件只在初稿完成后读。先按 `readability.md` 冷读实际任务，再集中修正事实、理解和表达问题。不要把一次改稿固定拆成许多轮，也不要为了让统计数字好看反复改写同一段。

## 先守住事实与任务

重新确认目标读者、允许的前置知识、主要使用场景和直接事实来源。版本、路径、命令、状态、因果、限制、规则强度和授权边界不得在改写中漂移。

沿一个主要场景从头读到尾，检查读者能否回答：什么情况下适用，需要提供什么，从哪里操作，会看到什么结果，失败后回到哪里。某项信息散落到多处、顺序颠倒或只能靠作者补充时，就在最接近操作的位置修正。信息要求不等于固定标题；页面已有自然结构时不另套模板。

## 一次处理理解与表达问题

按实际卡点安排修改顺序。通常先补事实和缺失步骤，再调整概念顺序，最后清理句子；某个卡点只需改一处时，不为凑流程重写其他段落。

- 术语或状态在解释前已经参与判断时，把说明移到首次依赖处。
- 命令、字段和代码块缺少用途、输入或结果时，就近补足必要语境。
- 一段切换多个产品、版本或状态时，按读者疑问拆层。
- 一句话同时承担结论、原因、边界和后果时，按语义节点拆开；复杂关系清楚时允许长句。
- 段落只换说法复述前文，或删掉后不影响任务与判断时，合并或删除。
- 无来源的精确细节、用户反馈和因果结论直接删除；材料不足时缩短内容。
- 连续抽象名词改回具体对象和动作，商业黑话、表演性排比、借喻堆砌和假口语还原成本义。
- 前后只靠“这”“它”切换对象时，把真正的对象写回来。

句长变异、连词密度和长句清单只是定位信号。不要按比例删连词，不要为制造节奏补短句或拉长句子。判断标准是读者能否顺着任务理解动作、条件和结果。

## 核对架构解释

架构内容应帮助读者完成操作、选择接入方式或定位故障。检查组件职责和流向是否沿同一个使用场景展开，限制是否有代码、接口或权威设计支持。只列目录、函数或组件名而没有说明它们怎样影响当前判断时，删掉或补上必要关系。

知识站场景至少要分清三种修改入口：正文事实错误回到 Markdown 与事实来源；正文正确但页面不一致时检查渲染；发布状态不明时查正式发布证据。材料无法证明原因时只描述可观察行为，不补造设计动机。

## 处理整篇重写

用户明确要求整篇重写时，可以放下原有句式，按同一组事实重新安排内容。页面 ID、URL、稳定锚点、命令、版本来源和必要限制仍要保留。整篇重写不改变页面职责、主题或产品行为；完成后重新走一遍同一使用场景，确认输入、操作、结果、失败恢复和组件关系没有遗漏。

## 用检测器清理表层问题

```bash
node ../scripts/check-style.mjs 稿件.md 页面.html
```

硬禁、警告和退出码以实际 `check-style.mjs` 及 `SKILL.md` 为准，不引用不存在的规则章节，也不另抄一份数量可能漂移的清单。命中硬禁时先找回原句事实，再用普通中文重写。检测器退出 0 只表示没有命中确定性硬禁；警告、可读性和事实仍须人工核对。

## 最后冷读

只给冷读者目标页和页面已声明的前提，请其完成主要任务并指出第一个需要猜测的位置。记录具体卡点和修改位置，不记录分数。随后对照事实源核对版本、命令、路径、状态、条件、因果和权限。冷读者能选择入口、准备输入、判断成功、找到失败恢复，并区分正文与渲染问题，才说明这次改稿解决了理解问题。
