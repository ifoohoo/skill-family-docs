# 可读性门细则

可读性门回答一个问题：声明的目标读者，在允许的前置知识下，能不能不靠猜测读懂当前结论和下一步。本文件给出检查项和检测器的指标口径。

## 五类理解障碍

### 1. 术语无解释

系统字段、命令、代码标识符保留原文，但第一次出现时给中文语境。陌生术语高频出现就加短术语表，低频只在首现处就近解释。术语表不能代替正文逻辑：决定当前判断的术语，正文首次依赖时仍要说明它在这里的作用。

### 2. 概念解释得太晚

关键概念、裁决代码、状态名在第一次被依赖前解释。当前段依赖后文才定义的对象、先给输出后说用途、状态码已参与结论但含义未讲——出现任何一种就调整顺序。

### 3. 一句话承载多个主要判断

复杂关系允许长句，但一句只留一个主要判断。结论、原因、边界、后果同时出现时按语义节点拆开。不机械压成统一长度，也不连续堆短句。

### 4. 命令和字段缺少上下文

命令出现说明用途或预期结果，字段出现说明它表达的事实，代码块前后说明用途、输入、输出或原因。不用「以上代码展示了」敷衍。

### 5. 信息密度过高

一段同时切换多个产品、版本、状态或标识符时先拆层。读者要比较、计数、执行用列表；维度相同字段稳定用表格。长论证不塞进表格单元格。

## 用真实任务冷读

只给冷读者目标页和页面已经声明的前提，不补充作者脑中的背景。请冷读者沿一条主要场景回答：

- 当前问题是否适用这项功能，应从哪个入口开始；
- 需要提供什么，在哪里操作；
- 什么结果表示成功，失败后回到哪里继续；
- 场景涉及哪些组件，正文错误和渲染错误分别应该处理哪里。

记录具体卡点及其位置，例如输入来源不明、操作入口缺失、成功条件无法观察，或组件职责不足以支持故障判断。“感觉不自然”和作者自报“已经讲清楚”都不能代替这些证据。

架构内容只在任务需要时出现。冷读者应能沿同一个操作追踪事实输入、Markdown 内容、配置选择、渲染结果和只读发布检查；不要求背目录或函数名。因果、版本与限制再对照代码、接口或权威设计核实。

## 检测器指标口径

`check-style.mjs` 报告句长变异、连词密度、长句率和长句清单。这些量化信号允许误报，只帮助找到值得重读的位置。检测器中的具体阈值和词表以脚本为准，不把它们改写成删词比例、句长目标或验收分数。

收到统计警告时回到对应段落，检查读者是否能跟上动作与判断。句子长但关系清楚可以保留；连词多但确实表达不同关系也可以保留。不为降低警告机械拆句、补短句、拉长句子或删掉必要条件。

## 不采用的机械规则

- 不要求每份文档都有术语表；
- 不固定「先读这段」式标题；
- 不要求一句只有一个主谓宾；
- 不要求三项并列一律列表化；
- 不要求按句长或连词比例改稿；
- 不把脚本退出码或统计分数当作可读性证明。
