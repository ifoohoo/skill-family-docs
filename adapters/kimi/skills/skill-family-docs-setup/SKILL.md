# 环境诊断与项目接入

setup 把环境检查与项目接入作为一段连续事务处理：先只读检查，再形成精确计划并展示影响，获得授权后执行计划，最后重新诊断和验证。检查或计划本身不构成写入授权。

## 确定请求状态

- 用户明确说“只读”“不要修改”或同等语义时，只完成诊断和计划，不反向询问授权。若存在安全的接入路径，提供一段可复制的接入请求。
- 用户只说“setup”“检查环境”“是否就绪”或同等语义时，先只读检查。全部就绪便直接结束；存在可处理的缺项时，在同一响应中展示计划并明确询问是否执行。
- 用户明确要求“接入项目”“准备环境并接线”或同等语义时，进入接入事务，但不能把该请求当成执行尚未展示计划的授权。仍须先完成只读检查，展示精确计划和影响，再询问是否执行。
- 用户明确引用并同意此前展示的计划时，只执行该计划，不重复询问。执行前重新核对版本、包管理器、目标文件、配置和冲突；依据发生变化时停止，重新展示计划并再次取得授权。

授权只覆盖已经展示且被用户明确同意的写入。不得把“帮忙看看”、首次提出接入、选择某个诊断选项或对结果的追问解释为执行授权。

## 只读检查

授权前不得修改项目文件、包清单、锁文件、配置、站点正文、覆盖快照、生成物、MEMORY、缓存或宿主持久状态，也不得执行会隐式安装依赖的 `npx --yes`、`npm exec --yes` 等命令。授权前的 Git 命令统一设置 `GIT_OPTIONAL_LOCKS=0`，禁止 `git status` 等只读查询刷新或写回索引；零写入验证同时核对工作区差异和 `.git/index` 字节或摘要不变。

1. 读取项目约束、包管理器、Node.js 版本来源与未提交改动。多个 Node.js 约束冲突时停止，不猜版本。
2. 找到 `public-release.json` 及目标 repo，确认 `site.dir`、`site.target`、`site.pages`、版本源和覆盖范围。新接入和已有配置都必须检查 `site.coverage.inputs` 实际展开的文件，不能只看模式文字或覆盖快照摘要。
3. 读取项目的依赖政策、包清单、锁文件和已有命令。CLI 来源的决策顺序固定：优先复用已有精确依赖；不可复用时，若项目允许则新增精确项目依赖；项目禁止持久依赖但明确允许外部 QA 工具时，才形成精确版本的临时调用计划；上述来源都不符合项目政策时，状态为“不满足前提”。
4. 从项目认可的官方分发源查询 `skill-family-doc-render` 最新稳定版，并记录查询方式、来源地址和返回的精确版本。npm 项目默认用宿主 Web 读取 npm registry，或运行 `curl -q -fsSL https://registry.npmjs.org/skill-family-doc-render` 禁用用户级 curl 配置，再从标准输出或内存解析 `dist-tags.latest`；不得重定向结果、写缓存或写日志。本地工作树、缓存、候选版本或浮动 `latest` 不能充当已发布证明。只有会持久写入的客户端可用，或无法核实官方版本时，状态为“不满足前提”，不得提出安装或执行安装。
5. 已有依赖或项目命令能定位精确版本时，核对包清单、锁文件与实际 CLI 是否一致。CLI 尚未安装时，通过宿主 Web，或从官方 registry 的精确版本 tarball 读取公开 README 与 Schema；使用 `curl -q` 和标准输出管道，不保存 tarball。必须在提出计划前核实每个配置字段、路径关系、页面清单字段和命令都受该精确版本支持；不能先安装再补查合同。无法零写入取得必要合同时，状态为“不满足前提”。
6. 需要新增依赖时，先确认依赖分区和保存精确版本的参数，再根据当前包管理器形成完整安装命令；不能把其他包管理器的示例当成当前计划。新格式项目必须显式声明 `site.format: "markdown-v1"` 与 `site.template: "editorial"`。检查 `pages.json` 中的站点元数据、分组、页面 ID、`role`、`kind`、顺序及 `inPager`，并确认每页对应 `<id>.md`。
7. 按项目事实选择稳定的覆盖输入：
   - 盘点源码、配置、权威文档和版本来源所在的真实目录与文件类型，再据此提出模式。
   - 模式只使用普通相对路径、`*` 和 `**`。现有合同没有排除字段、否定 glob 或通用忽略引擎，不能写入这些语法。
   - 按渲染器的文件系统语义逐项展开候选模式，核对每个命中文件。缓存、日志、安装依赖、生成产物和临时构建内容不能进入覆盖；合法但尚未跟踪的源码或正文仍是产品输入。
   - 现有模式命中不稳定文件时，报告具体模式、意外命中文件及收窄方向。不能删除缓存或提前刷新覆盖快照来掩盖问题。
8. 读取项目现有文档检查、`check:release-docs` 和 release-skill `hooks.docs`。记录原命令的顺序、工作目录、环境和失败传播。判断字段不存在时，必须完整解析结构化配置，或搜索完整文件并核对匹配区段；被截断的输出不能证明字段不存在。
9. 配置完整且 CLI 已可用时，在 `public-release.json` 所在目录运行只读检查：

   ```bash
   skill-family-doc-render --check-project --repo <name>
   ```

   该命令检查输入与公开安全、覆盖状态、正文确定性规则、渲染一致性、内部链接和资源。退出 0 表示通过，1 表示内容或产物需要处理，2 表示输入或配置错误。

## 识别已有站点

发现项目已有自定义渲染器、HTML 源或自有站点命令时，不能直接判定 skill-family-docs“不适用”，也不能由 setup 修复自定义渲染器。根据项目事实区分四种结果：

- 保留现状：继续使用原工具链，setup 不写入，只说明缺少哪些 skill-family-doc-render 能力及可复制的后续请求。
- 兼容接入：保留原工具链，同时接入不会争用源目录、输出目录、命令或发布钩子的 skill-family-doc-render 检查。计划必须说明两条工具链各自负责什么。
- 有冲突：两条工具链会争用路径、配置、生成物或检查入口。列出具体冲突和可选路径，不自动覆盖，也不顺手修复原工具链。
- 显式迁移：只有用户明确选择迁移时才准备新合同。setup 只处理获批的依赖、配置和检查接线；正文转换、目录调整和首次生成交给 `skill-family-docs-render-site`，不得在正文缺失时提前刷新覆盖。

## 输出诊断与计划

诊断结果必须先给出一个状态：

- 已就绪：依赖、配置和只读检查均满足合同，无需变更，也不询问授权。
- 已接入，站点待处理：依赖和配置已经接好，但正文、覆盖或渲染检查需要由 render-site 处理。列出实际失败和可复制的恢复请求，不把内容问题包装成 setup 缺项。
- 可接入：存在可由 setup 安全补齐的缺项。
- 有冲突：现有路径与候选接入不能同时安全成立，需要用户选择。
- 不满足前提：Node.js、官方版本来源、依赖政策或必要项目事实不足，当前不能形成可执行计划。
- 保留现状：用户选择继续使用自定义工具链，当前不采用 skill-family-doc-render。说明能力差异和后续入口，不表示 skill-family-docs 已就绪。

逐项列出实际值、覆盖模式及命中文件、缺失项和冲突。状态为“可接入”时，精确计划必须包含：

1. 官方核实的精确已发布版本、查询方式和来源地址。
2. 当前包管理器的完整安装或调用命令，包括会改变行为的环境变量、缓存和日志位置；若复用已有依赖，明确写“保持不变”。
3. 将创建、修改和保持不变的具体路径；对每个文件列出全部新增或变化字段及其精确值，并说明作用。新配置不能保留待执行时再决定的路径、令牌、页面 ID 或其他占位值；安装产生的 `node_modules`、缓存、日志等目录也必须列出。
4. 预计运行的命令、工作目录，以及会产生的本地影响。
5. 明确不会执行的动作，包括宿主插件安装、发布、整站正文生成、未获批迁移和无关文件修改。
6. 执行后的成功信号，包括依赖与锁文件一致、目标配置有效、既有检查继续传播失败，以及只读项目检查的实际退出码。

裸调用或一般检查请求在计划末尾明确询问是否按这份计划执行。用户明确只读时不提问，改为提供可复制的请求，例如“请使用 skill-family-docs-setup 按以上计划接入当前项目”。状态为“有冲突”时列出保留现状、兼容接入和显式迁移中实际可行的选项，请用户选择；状态为“不满足前提”时只给解除阻塞所需的事实或动作，不假装已有可执行计划。

## 执行已授权计划

1. 在首次写入前重新执行会影响计划的只读检查，并验证整份计划的全部命令、配置值和后续写入都已确定且符合精确版本合同。任何剩余字段未定，或精确版本、包管理器、文件内容、目标路径、合同及冲突发生变化时，不得先执行计划的一部分；重新展示完整计划并取得授权。
2. 按计划接入 CLI。实际命令、环境变量、缓存和日志位置必须与获批计划一致；增加计划外命令、参数、目录或重定向路径时先停止并重新授权。只有项目允许添加工具依赖时，才用当前包管理器写入精确版本并更新现有锁文件。项目禁止持久依赖但明确允许外部 QA 工具时，获批后才可执行计划中展示的精确版本临时调用；该路径不修改 `package.json` 或锁文件，接入的检查命令仍须保留精确版本。
3. 只补齐获批的 `site` 配置、版本源、覆盖输入、内容目录和 `pages.json`。产品类型只能依据项目权威说明选为 `plugin` 或 `library`。
4. 把 `--check-project --repo <name>` 接入项目现有文档检查。已有命令时保留原顺序和失败传播，不替换或跳过原命令；已有 `hooks.docs` 时只在其调用链中组合新检查。无法安全组合时停止，不另建旁路 hook。
5. 所需源文件已经存在且覆盖输入经过语义核对后，才执行 `--refresh-coverage --repo <name>`。读取覆盖锁中的输入列表，确认产品输入在内且缓存与生成物不在内。新项目只有 setup 配置完成但正文尚未生成时，状态是“接入配置完成，等待首次生成”，不能刷新覆盖，也不能报告知识站已完成。
6. 重新诊断依赖、配置、覆盖和检查接线，再运行适用的只读项目检查。报告实际修改、命令、退出码和仍未执行的动作。

项目未采用 release-skill 时，只报告“本地接入完成，发布集成未配置”。不创建远程、发布目标或猜测的 hook。setup 不安装宿主插件，不发布，不生成或改写整站正文，也不修复自定义渲染器。

第二次执行相同接入请求时，配置和锁文件必须保持原字节。只有配置、正文、覆盖、渲染和只读项目检查均满足合同，才报告“已就绪，无需变更”。配置已经接好但正文尚未生成时，仍报告“接入配置完成，等待首次生成”；正文、覆盖或渲染检查有待处理时，报告“已接入，站点待处理”。结果列出实际检查命令、退出码和仍未执行的发布或宿主动作。
